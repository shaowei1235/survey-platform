# 現行業務と課題

<span class="status-chip">Requirements / As-Is</span>

## 調査の背景

従業員満足度（ES）調査は、設問作成、配信、回答、集計、経営報告まで複数の担当者とツールをまたぐ業務です。導入前は汎用フォーム、メール、Excel、共有ファイルで運用されており、フォーム単体ではなく**業務全体の断絶**が課題でした。

<ol class="journey">
  <li>人事が設問を作成</li>
  <li>メールで全社配信</li>
  <li>従業員が回答</li>
  <li>CSV を取得</li>
  <li>Excel で再集計</li>
  <li>手作業で報告</li>
</ol>

## 現行フローで起きていたこと

| 領域 | 現行のやり方 | 業務への影響 |
| --- | --- | --- |
| アンケート作成 | 前年フォームをコピー、または作り直す | 設問の変更履歴と状態を一元管理できない |
| 回答者属性 | 自己申告または回答後の名簿照合 | 部門・職級・年代別の集計精度が落ちる |
| 回収状況 | 人事が部門長へメールで催促 | 回収率の把握と催促のタイミングが属人的になる |
| クロス集計 | 担当者のローカル Excel | 部門 × 設問 × 属性の分析に時間がかかる |
| 自由記述 | 人事が全文を読み、数件を選ぶ | 選定基準が一定せず、再検証しにくい |
| 権限 | ファイルを持っている人が閲覧できる | 他部門データや原文の共有範囲を制御しにくい |
| 匿名性 | 少人数セルの扱いが標準化されていない | 小規模部署では回答者を推測できる可能性がある |
| 経営報告 | 数字と要約を別資料で作成 | 結論から根拠へ遡るのに時間がかかる |

## 課題の優先順位

課題は「情報漏えい・誤判断」「運用負荷」「体験」の順で評価しました。UI の利便性だけを先に改善しても、権限や匿名性が曖昧なままでは業務利用できないためです。

<div class="decision-grid">
  <article class="decision-card">
    <span class="eyebrow">Priority 1</span>
    <h3>データ境界を明確にする</h3>
    <p>ロールと組織スコープを API のクエリ条件として強制し、ファイル共有に依存しない閲覧範囲を作る。</p>
  </article>
  <article class="decision-card">
    <span class="eyebrow">Priority 2</span>
    <h3>匿名性を仕様にする</h3>
    <p>回答数が 5 未満の集計セルを非開示にし、自由記述は識別子除去後の抜粋だけを分析へ渡す。</p>
  </article>
  <article class="decision-card">
    <span class="eyebrow">Priority 3</span>
    <h3>集計を再現可能にする</h3>
    <p>回答時点の組織属性を保存し、同じ条件なら同じ結果を返す構造化集計を API に集約する。</p>
  </article>
  <article class="decision-card">
    <span class="eyebrow">Priority 4</span>
    <h3>結論と根拠をつなぐ</h3>
    <p>AI は文章生成に限定し、表示する数値は SQL 集計から取得。回答には検証用エビデンスを添付する。</p>
  </article>
</div>

## To-Be で目指した状態

| Before | After |
| --- | --- |
| フォームと集計表が別管理 | 作成・公開・回答・終了を一つのライフサイクルで管理 |
| 回答者が属性を入力 | 組織マスタから回答時点の属性を自動保存 |
| 全件 CSV を人が加工 | 権限内のクロス集計を画面と Excel で提供 |
| 少人数部署も値が見える | n&lt;5 のセルは平均値を非開示 |
| 部門長への共有粒度が不統一 | 所属部門と配下組織だけをクエリ時に取得 |
| 要約と数字が別資料 | 結論・集計根拠・引用・グラフ ID を一つの応答に統合 |

# 認証・認可

<span class="status-chip">Implementation / Identity & access</span>

## 認証フロー

第一期は社員番号とパスワードによるローカル認証を採用しました。認証方式と認可ロジックを分離しているため、将来 OIDC を追加しても部門スコープや業務権限の判定を維持できます。

```text
1. POST /auth/login
2. argon2id でパスワード照合
3. Access token（15分）+ Refresh token（7日）を発行
4. GET /me でロールと展開済みスコープを取得
5. 各 API リクエストで DB の最新ロールを再確認
```

## トークンの扱い

| Token | クライアント | サーバー |
| --- | --- | --- |
| Access token | memory + `sessionStorage` | JWT 署名、`sub`・`company_id`・有効期限を検証 |
| Refresh token | `sessionStorage` | SHA-256 ハッシュ、期限、失効日時を保存 |

Refresh 成功時は新しいペアを発行し、古い Refresh token を無効化します。ユーザーが存在しない場合とパスワード不一致は、同じ `INVALID_CREDENTIALS` を返してアカウント列挙を防ぎます。

## RBAC と組織スコープ

認可は次の四要素で判断します。

```text
主体 User
  × Role
  × Department scope
  × Resource / Action
```

### 例: 部門長がクロス集計を見る場合

1. `dept_manager` ロールがあるか確認する。
2. ロールに割り当てられた部門を取得する。
3. 再帰 CTE で配下課を展開する。
4. リクエストの `department_id` が集合内か検証する。
5. 集計 SQL の WHERE に許可された ID を入れる。

範囲外 ID を指定した場合は 403 を返し、0 件の成功応答へ置き換えません。

## 操作権限

| リソース / 操作 | system_admin | hr_planner | executive | dept_manager | employee |
| --- | --- | --- | --- | --- | --- |
| ユーザー・ロール管理 | 可 | 可 | — | — | — |
| アンケート作成・公開 | — | 可 | — | — | — |
| 全社分析 | — | 可 | 読み取り | — | — |
| 自部門分析 | — | 可 | 読み取り | 読み取り | — |
| 回答送信 | — | — | — | — | 本人のみ |

複数ロールを持つ利用者は、許可操作と部門範囲の和集合を持ちます。ただし、一般従業員ロールだけでは分析 API を利用できません。

## 認可と匿名化の分離

権限があっても、すべての値が見えるわけではありません。人事や経営層にも n&lt;5 の平均値は返さず、自由記述の原文を個人単位で閲覧する API は提供しません。

```text
認可: その部門の集計へアクセスできるか
匿名化: アクセスできても、そのセルの値を公開できるか
```

この二段階を分けることで、「正しいロールだから個人が特定できる値も見せる」という設計上の抜けを防いでいます。

## 将来の SSO への備え

外部 IdP を追加する場合は、ログイン時の本人確認とトークン発行部分を置き換えます。業務ロール、部門ツリー、API ごとの resource/action 判定はアプリ側に残すため、SSO 導入を理由に認可モデルを作り直す必要がありません。
